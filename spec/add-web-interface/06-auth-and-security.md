# 06. Аутентификация и безопасность

Веб-интерфейс даёт полный контроль над загрузками и умеет безвозвратно удалять файлы.
Поэтому безопасность — не «добавим логин в конце», а часть контракта.

## 1. Активы и границы доверия

| Актив | Где | Последствия компрометации |
|---|---|---|
| Доступ к Transmission/Torrserver/Jackett | LAN, без собственной аутентификации у части сервисов | чужие загрузки, удаление файлов, стриминг |
| Файлы на диске NAS | `path.*` | безвозвратная потеря данных |
| Пароли веб-пользователей | `settings.json` (хеши) | вход в UI |
| Сессионные токены/CSRF | память, cookie | угон сессии |
| Названия раздач и ссылки | ответы Jackett/трекеров | XSS, SSRF |

Границы: браузер пользователя ↔ веб-сервер (`torrentino`) ↔ Jackett/Transmission/
Torrserver. Telegram в этой цепочке не участвует.

## 2. Модель угроз

| # | Угроза | Вектор | Меры |
|---|---|---|---|
| T1 | Подбор пароля | `/login` | PBKDF2 600k, rate limit по IP и имени, задержка, lockout-окно, логирование |
| T2 | Перехват пароля/сессии | HTTP без TLS | TLS на nginx (443), `Secure` cookie, HSTS; приложение слушает loopback |
| T3 | CSRF | чужая страница шлёт POST | SameSite=Lax, CSRF-токен, проверка Origin/Referer |
| T4 | Угон cookie | XSS/кража | `HttpOnly`, CSP, короткий absolute TTL, сервер хранит только хеш токена |
| T5 | XSS через название раздачи/трекер | данные Jackett | `html/template`, запрет `template.HTML` для данных, CSP без `unsafe-inline` |
| T6 | Open redirect | `next` после логина | только путь под `web.base-path`, без схемы/хоста/`//`/`..` |
| T7 | Path traversal при удалении | имя/путь элемента | путь строится на сервере из доверенного элемента; `Clean` + проверка корня |
| T8 | SSRF через `.torrent`/постер | ссылка из результата трекера | только http(s), таймаут, лимит размера, bencode-проверка, без редиректов на файловые схемы |
| T9 | Destructive-запрос из чужой вкладки/скрипта | POST delete | CSRF + проверка `Origin` + аудит; подтверждения нет (паритет с Telegram) |
| T10 | Утечка секретов в логи | ошибки/URL | не логировать пароли, токены, cookie; request-id вместо тела |
| T11 | DoS логином/поиском | много запросов | rate limit, лимиты тела/запроса, контекст и таймауты |
| T12 | Подделка/сдвиг индекса элемента | `select:999`, автообновление переставило строки | проверка границ + выбор по стабильному ключу, 409, действия только над серверным элементом |
| T13 | Кликджекинг | iframe | `frame-ancestors 'none'`, `X-Frame-Options: DENY` |
| T14 | Утечка через `/healthz` | публичный эндпоинт | только `{"status":"ok"}`, без версий/конфигов |
| T15 | Соседнее приложение на том же origin | два других приложения на общем 443/домене | **закрыт**: основной деплой на отдельном поддомене `torrentino.example.com`; path-fallback `/torrentino` возвращает риск |

## 3. Пароли и аккаунты

- Аккаунты — в `settings.json`:

  ```json
  "web": {
    "users": [
      { "name": "denis", "password-hash": "pbkdf2-sha256$600000$<salt>$<hash>" }
    ]
  }
  ```

- Хеш: PBKDF2-HMAC-SHA256, `crypto/pbkdf2` (stdlib Go 1.24+), соль 16 байт,
  ключ 32 байта, итераций 600 000 (минимум 100 000, максимум 2 000 000).
  Формат: `pbkdf2-sha256$<iterations>$<base64 salt>$<base64 key>`.
- Проверка: `subtle.ConstantTimeCompare`; для несуществующего пользователя вычисляется
  фиктивный хеш, чтобы время ответа не выдавало наличие имени.
- Генератор хеша: `torrentino -hash-password` — читает пароль из stdin (не из argv!),
  печатает строку для конфига. Пример без эха:

  ```bash
  read -rs PASSWORD && printf %s "$PASSWORD" | ./torrentino -hash-password
  ```

  Флаг не требует загрузки `settings.json` и завершает процесс, ничего не запуская.
- Имена пользователей уникальны (сравнение без учёта регистра), непустые, ≤ 64 символов.
- Аккаунтов может быть несколько (как несколько ID в Telegram `users-list`); все
  равноправны, у каждого своя сессия и свои экраны.
- Пароль в открытом виде нигде не хранится и не логируется.
- Смена пароля — правка `settings.json` + рестарт; активные сессии при рестарте исчезают.
- Регистрации, сброса пароля, 2FA и OIDC в v1 нет (см. 01, N4).

## 4. Сессии

- Токен: 32 случайных байта (`crypto/rand`), base64url; в cookie — только он.
- На сервере хранится `sha256(token)`: дамп памяти не даёт готовых cookie.
- Cookie: `torrentino_session=<token>; HttpOnly; SameSite=Lax; Path=<base>; Max-Age=<abs>`
  плюс `Secure` при TLS (или при `web.secure-cookies: true` за прокси). В основном
  деплое `base=/`, `Path=/`, cookie **host-only** (без `Domain`) и уходит только на
  `torrentino.example.com`. В fallback с префиксом — `Path=/torrentino`.
  Префикс `__Host-` не используется.
- TTL: idle 12 ч (скользящий, обновляется при запросе), absolute 168 ч.
  Оба настраиваются; значения проверяются (idle < absolute).
- Логин всегда создаёт **новый** токен (защита от фиксации); старые сессии пользователя
  не инвалидируются, но их число ограничено.
- Logout: POST + CSRF, удаляет запись и ставит просроченную cookie с тем же `Path=<base>`.
- Store: `map[[32]byte]*Session` под `RWMutex`, максимум 512 сессий, GC раз в минуту.
  При переполнении вытесняется самая старая по `LastSeen`.
- Рестарт процесса = все сессии потеряны (осознанно: нет внешнего хранилища).

## 5. CSRF

- Токен: 32 случайных байта на сессию, привязан к ней.
- Передаётся: скрытым полем `csrf` в каждой форме и заголовком `X-CSRF-Token`
  (JS добавляет его всем htmx-запросам через `htmx:configRequest`).
- Проверка: `subtle.ConstantTimeCompare`; отсутствие/несовпадение → `403`.
- Дополнительно: для POST с заголовком `Origin` он должен совпадать с ожидаемым
  `scheme://host` (с учётом trusted proxy и `X-Forwarded-Proto`); при отсутствии
  `Origin` (curl) достаточно валидного токена.
- `SameSite=Lax` — вторая линия: cross-site POST не получает cookie.
- Логин защищён pre-auth токеном: `GET {base}/login` ставит короткоживущую cookie
  `torrentino_login` с `Path=<base>` и кладёт токен в форму; после успешного входа
  cookie удаляется.
- Все мутации — только POST; GET-эндпоинты ничего не меняют.

## 6. Авторизация

- Доступ к `{base}/find`, `{base}/downloads`, `{base}/torrserver`, `{base}/ui/*`,
  `{base}/find/torrent` — только с валидной сессией. Публичны: `{base}/login`,
  `{base}/healthz`, `{base}/static/*`, `{base}/favicon.ico`.
- Middleware возвращает `303`/`HX-Redirect` на логин с `next` (только путь под `base`).
- В v1 все пользователи равноправны. Клиент не может подставить чужой элемент:
  действия адресуются индексом в серверном списке сессии, все данные берутся из него.
- Будущая read-only роль: поле `web.users[].read-only`, проверка в `web.actionAllowed`
  и скрытие destructive-кнопок; на сервере — обязательная проверка, не только UI.

## 7. Заголовки безопасности

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none';
  base-uri 'none'; object-src 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY
Permissions-Policy: geolocation=(), camera=(), microphone=()
Strict-Transport-Security: max-age=31536000   # только при TLS
Cache-Control: no-store                       # всё, кроме статики/healthz
```

- Никаких внешних CDN/шрифтов: `script-src 'self'` и `style-src 'self'` реальны.
- htmx: `htmx.config.allowEval = false`; не используются `hx-on`, event-фильтры и inline
  выражения — это позволяет обойтись без `unsafe-eval`.
- Если появится WASM (07), CSP потребует `'wasm-unsafe-eval'` в `script-src`; это одно
  из последствий, которое нужно взвесить при пересмотре решения.

## 8. TLS и сеть

- Деплой: интернет/домен, nginx на 443 (там же два других приложения), TLS терминируется
  nginx; `torrentino` слушает `127.0.0.1:8088` и не публикуется напрямую. Основной
  origin — `torrentino.example.com` (`base-path: "/"`); старый путь
  `/torrentino` на базовом домене — только редирект.
- Поддомен — отдельный origin: соседние приложения на `example.com` не могут
  читать наши страницы/CSRF (T15 закрыт). Fallback-режим с путём снова объединяет origin.
- Варианты:
  1. nginx с TLS (используется в деплое), приложение на loopback;
  2. встроенный TLS: `web.tls.cert`/`web.tls.key` (PEM) — для прямого доступа без прокси;
  3. HTTP в доверенной LAN — только как отладочный режим, не для паролей.
- За прокси: `web.trusted-proxies` (CIDR; в деплое `127.0.0.1/32` или адрес nginx),
  из `X-Forwarded-For` берётся первый недоверенный адрес справа, из `X-Forwarded-Proto` —
  схема для `Secure` cookie, HSTS и проверки `Origin`. Не доверять этим заголовкам без
  списка прокси.
- `web.secure-cookies: true` обязателен, если TLS терминирует nginx.
- HSTS (`max-age=31536000; includeSubDomains`) ставится на nginx для всего домена;
  приложение может дублировать заголовок при встроенном TLS.
- Порт 8088/tcp должен быть доступен только с loopback (или из docker-сети nginx),
  но не из интернета.

## 9. Валидация ввода

- Команда: строгий парсер (`select:`, `page:`, `sort:`, `filter:`, `controls:`,
  `action:`), индексы — только ASCII-цифры с проверкой переполнения и границ.
- `sort`/`filter` — только значения из дескрипторов `core`, иначе `400`/no-op.
- `action` — только из `AvailableActions` для выбранного элемента, иначе `409`.
- `q`: trim, длина 1–256, отбрасывание управляющих символов; URL-кодирование выполняет
  `url.QueryEscape` в `api/jackett`.
- Тело запроса ≤ 64 КБ, заголовки ≤ 16 КБ.
- `next`: только путь под `web.base-path` (в основном деплое, например, `/downloads`;
  в fallback — `/torrentino/downloads`), без `//`, `\`, схемы, хоста и `..`;
  иначе — `base/find`.
- `web.base-path`: ведущий `/`, без хвостового `/`, `//`, `..`, query/fragment;
  иначе конфиг не проходит валидацию (см. 08).
- Имя файла `.torrent`: очистка CR/LF/кавычек/`\`/`/`, обрезка до 150 символов;
  заголовок формируется `mime.FormatMediaType`/RFC 5987, а не конкатенацией.
- Никаких URL, путей и ID из формы, кроме индексов и имён команд.

## 10. XSS и внешние ссылки

- Все данные рендерятся через `html/template`; запрещено `template.HTML` и
  `template.URL` для значений из `jackett.Result` (Title, Tracker, Details, Poster).
- `Details` перед рендером проверяется: только `http`/`https`, иначе ссылка не выводится.
- Poster не отображается в нашем UI (только передаётся в Torrserver), но и там
  проверяется схема.
- CSP запрещает inline-скрипты и внешние источники; шаблоны не содержат `onclick` и
  `<script>` с данными.

## 11. SSRF и загрузка `.torrent`

- URL для скачивания берётся только из серверного элемента списка (результат Jackett),
  не из запроса. Это не устраняет риск полностью: трекер/Jackett могут вернуть ссылку
  на внутренний адрес.
- Меры: только `http`/`https`; таймаут 30 с; лимит 25 МБ; максимум 3 редиректа;
  проверка bencode (`d` в начале); содержимое никогда не интерпретируется как HTML/JS;
  ответ отдаётся как `application/x-bittorrent` + `nosniff` + attachment.
- Скрейпинг постера: 10 с, только http(s), максимум 2 МБ, результат — только строка
  URL для Torrserver; ошибки не фатальны.
- Остаточный риск: внутренний HTTP-сервис может получить запрос от имени NAS. Это
  свойство существующего Telegram-сценария; для web оно дополнительно ограничено
  форматом ответа.

## 12. Destructive-действия

- Удаление выполняется сразу, как в Telegram: POST + CSRF + проверка `Origin`; отдельного
  подтверждения нет. Это осознанное решение владельца (паритет), риск — в §15.
- Действие адресуется не «индексом в клиенте», а выбранным элементом по стабильному
  ключу (`id:`, `path:`, `hash:`): если автообновление переставило строки, удаление
  не затронет соседнюю; если элемент исчез — `409`, удаления нет.
- Сервер использует только свои данные:
  - Transmission: `ID` из списка сессии → `TorrentRemove(DeleteLocalData: true)`;
  - диск: `DownloadDir` + `Name` из списка, `filepath.Clean`, проверка, что итоговый
    путь лежит внутри одного из `path.default/movie/series`; иначе `409` и лог;
  - Torrserver: `hash` из списка.
- Никакого «удалить всё» и массовых операций в v1.
- Аудит: кто, что, куда, результат, request-id. Для диска — полный путь.
- После удаления элемент убирается из списка и снимается выбор.
- UI: кнопка `delete` красная, с `title` о необратимости; для `on disk` — явный
  `title="Delete files now — cannot be undone"`.

## 13. Секреты, логи, аудит

- `settings.json` содержит токен бота, API-ключ Jackett и хеши паролей. Рекомендуется
  `chmod 600` и владелец-сервисный пользователь (сейчас файл в рабочем дереве может быть
  664 — это стоит поправить в деплое, см. 08).
- В логи не попадают: пароли, cookie, CSRF, `Authorization`, тела запросов целиком.
- Access log: `web: ip=… user=… method=… path=… status=… dur=… request_id=…`.
  Поисковый запрос логируется только на уровне debug (может быть приватным).
- Аудит-события: login ok/fail, logout, rate-limit, delete (с деталями), torrserver delete,
  смена конфигурации (старт с версией), ошибки upstream.
- `utils.LogError` остаётся основным способом логирования ошибок.

## 15. Остаточные риски

| Риск | Оценка | Комментарий |
|---|---|---|
| Соседнее приложение на том же origin | закрыт поддоменом | основной деплой — `torrentino.example.com`; path-fallback `/torrentino` возвращает риск |
| Случайное удаление (нет подтверждения) | средний | паритет с Telegram; компенсируется красной кнопкой, аудитом, будущей read-only ролью/корзиной |
| HTTP без TLS | низкий (в деплое TLS на nginx) | только отладочный режим; `Secure` cookie, HSTS |
| Скомпрометированное устройство в LAN | средний | сессия даёт полный контроль; ограничить сеть/аккаунты |
| Вредоносная раздача | низкий | XSS экранируется, SSRF ограничен форматом/лимитами |
| Один общий уровень прав | низкий | все пользователи — «админы»; read-only — будущее |
| Нет 2FA | низкий/средний | компенсируется сложным паролем и rate limit |
| Потеря сессий при рестарте | низкий | повторный вход; зато нет хранения токенов |
| Память под сессии | низкий | лимит 512 + GC |

# Веб-интерфейс Torrentino — проект

**Статус:** Draft v0.1 · 17.10.2026; v1 реализован и развёрнут
**Предмет:** второй интерфейс к `torrentino`, открываемый в браузере, с паритетом функций Telegram-бота  
**Реализация:** v1 реализован в `common/list`, `core/` и `web/` и развёрнут на
`https://torrentino.example.com/` (nginx 443 → `127.0.0.1:8088`, certbot
webroot). Публичная web-приёмка пройдена; ручной Telegram-smoke остаётся за владельцем.
Деплой и приёмка — по [08](08-deployment-and-ops.md) и [09](09-testing-and-acceptance.md);
фактический статус по этапам — в [10, §1.1](10-roadmap-and-risks.md#11-фактический-статус-на-18102026).

## Зачем это нужно

Сейчас единственный UI бота — Telegram. Сам `torrentino` при этом не зависит от Telegram:
Jackett, Transmission и Torrserver живут на NAS отдельно, а бот лишь вызывает их API.
Но если Telegram недоступен (сбой API, блокировка, проблемы с клиентом/аккаунтом),
управлять загрузками невозможно, хотя все нужные сервисы работают.

Нужен параллельный интерфейс, который:

1. открывается в обычном браузере и не требует Telegram вообще;
2. воспроизводит весь UI-функционал бота: поиск, загрузки, Torrserver, сортировки,
   фильтры, пагинацию и все действия;
3. работает, даже если Telegram-часть бота в этот момент не может достучаться до API;
4. не ломает существующий Telegram-сценарий и текущий деплой (один бинарник).

## Кратко о рекомендуемом решении

- **Веб-сервер в том же процессе и бинарнике** `torrentino`, включается `web.enabled`.
  Это переиспользует `common.Settings`, клиентов `api/*` и не добавляет второй unit.
- **Server-side rendering**: Go `html/template` + вендорный htmx (один статический файл) +
  небольшой `app.js` для опроса, CSRF-заголовка и фокуса. Без npm, сборки фронтенда и SPA.
- **Свои веб-аккаунты** (несколько равноправных, как несколько ID в `users-list`):
  `web.users` с PBKDF2-хешами (`crypto/pbkdf2`, stdlib Go 1.24), серверные сессии
  в памяти, CSRF-токены, rate limit на логин. Telegram `users-list` для веб-доступа
  не используется: вход не должен зависеть от Telegram.
- **Состояние экрана на сервере**, по одному на тип экрана в сессии. Сортировка,
  фильтры, пагинация и выбор элемента переиспользуют `List`/`View`, вынесенные из
  `common/paginator` в UI-агностичный `common/list`. Это исключает расхождение
  поведения двух интерфейсов — в том числе тонкую логику мультисортировки и фильтров.
- **Обновление `/downloads`** — htmx-опрос раз в 5 с (как тикер в боте), с паузой,
  когда вкладка скрыта. WebSocket/SSE для v1 не нужны.
- **Ассеты и шаблоны встроены** через `embed`; `update-service.sh` и systemd-юнит
  не меняются. Основной деплой — поддомен `torrentino.example.com` с
  `web.base-path: "/"`; поддержка префикса (`base-path`) остаётся для fallback, а старый
  путь `/torrentino` на базовом домене отдаёт редирект.
- **WebAssembly рассмотрен и отклонён для v1; решение согласовано.** Спайк показал:
  минимальный Go/wasm-клиент (`net/http` + `encoding/json` + `syscall/js`) —
  10 344 298 Б, 2 755 556 Б в gzip, то есть больше релизного бинарника всего бота
  (8 093 988 Б) по несжатому размеру. Для сравнения, htmx — десятки килобайт.
  Подробный разбор, условия пересмотра и план миграции — в
  [07-wasm-option.md](07-wasm-option.md).

## Что входит в v1

| Экран | Функционал |
|---|---|
| `/find` | поиск по Jackett, список результатов, флаги 📥/🎦/📎/🧲, сортировки size/seeds/peers/file, фильтр по трекеру, пагинация, действия download/series/movie, torrsrv, скачивание `.torrent`, ссылка на web page |
| `/downloads` | Transmission + файлы на диске, статусы и иконки, сортировки date/name/size/dir, фильтр по статусу, пагинация, pause/start/delete, футер с диском, автообновление 5 с |
| `/torrserver` | список раздач, сортировка по размеру, пагинация, удаление |
| Общее | логин/логаут, несколько аккаунтов, сессии, CSRF, удаление сразу как в Telegram, понятные ошибки, мобильная вёрстка, работа под `torrentino.example.com` за nginx |

## Ключевые решения

| # | Решение | Кратко |
|---|---|---|
| D1 | Веб-сервер в том же процессе и бинарнике | переиспользование конфига и клиентов, один unit; Telegram-сбой не фатален при включённом web |
| D2 | SSR (`html/template`) + htmx, без SPA | минимум кода и зависимостей, сервер уже владеет состоянием |
| D3 | WebAssembly не используется в v1 | размер клиента, дублирование рендеринга, отладка; API оставляем готовым к SPA |
| D4 | Состояние экранов на сервере, per-session | паритет с пагинатором, отсутствие глобального состояния Telegram |
| D5 | Несколько веб-аккаунтов и сессий | вход не зависит от Telegram; `users-list` не переиспользуется |
| D6 | htmx-опрос `/downloads` раз в 5 с | проще SSE/WS, совпадает с текущим поведением |
| D7 | Общий UI-агностичный `list.View` и `core` | одна реализация сортировок/фильтров/действий для двух UI |
| D8 | `embed` статики и шаблонов | по-прежнему один бинарник и прежний деплой |
| D9 | Поддомен `torrentino.example.com`, приложение на loopback за nginx | отдельный origin; TLS и 443 — на nginx, порт приложения не публикуется |
| D10 | Удаление сразу, как в Telegram | один клик, но CSRF, проверка пути и аудит; выбор привязан к стабильному ключу элемента |
| D11 | JSON API отложен | HTML-эндпоинты покрывают v1; JSON появится только с SPA/WASM |
| D12 | Поддомен `torrentino.example.com`, `base-path: "/"` | отдельный origin закрывает same-origin риск; путь `/torrentino` — только временный редирект |

## Оценка

Один опытный разработчик, знакомый с репозиторием, без смены требований:
**≈ 22–31 человеко-день** (5–6 недель при неполной занятости), включая поддомен,
сертификат и конфигурацию nginx. Разбивка и допущения — в
[10-roadmap-and-risks.md](10-roadmap-and-risks.md). WebAssembly в план не входит:
решение согласовано, вариант остаётся возможным расширением (+8–12 дней).

## Принятые решения

1. **WASM:** в v1 не нужен, делаем SSR + htmx.
2. **Доступ:** интернет/домен через nginx на 443. Основной вариант —
   `https://torrentino.example.com/` (`base-path: "/"`, отдельный сертификат,
   приложение на `127.0.0.1:8088`). Путь `https://example.com/torrentino/`
   остаётся только как временный редирект на поддомен; поддержка `web.base-path`
   сохраняется для fallback.
3. **Пользователи:** несколько равноправных аккаунтов (как несколько ID в
   `users-list`), без ролей в v1.
4. **Удаление:** сразу, как в Telegram, без отдельного подтверждения. Защита —
   аутентификация, CSRF, проверка пути и аудит; выбор элемента привязан к стабильному
   ключу, чтобы автообновление не перенаправило действие на соседнюю строку.
5. **Язык UI:** английский, как в боте.

Остаются открытыми (рекомендуемые значения уже в проекте): плеер Torrserver в нашем UI —
нет; сохранение сессий после рестарта — нет; изоляция вкладок — одна на тип экрана;
лимит числа результатов — нет; история действий в UI — нет, только аудит в лог.

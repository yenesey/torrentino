# 07. Вариант на WebAssembly

## 1. Вопрос

Можно ли сделать клиентскую часть веб-интерфейса на Go, скомпилированном в WebAssembly,
чтобы переиспользовать код и обойтись без JavaScript-экосистемы? Ниже — оценка, замеры
и решение.

## 2. Метод

Спайк выполнен локально на Go 1.25.5 (проект целиком собирается и на 1.24; для wasm
использован установленный toolchain):

- минимальная программа: `net/http` (fetch), `encoding/json`, `syscall/js`, один
  HTTP-запрос и разбор JSON;
- сборка: `GOOS=js GOARCH=wasm go build -trimpath -ldflags "-s -w"`;
- сжатие: `gzip -9`;
- для сравнения — релизная сборка бота `go build -ldflags "-s -w"`.

| Артефакт | Размер | gzip -9 |
|---|---:|---:|
| Минимальный Go/wasm-клиент | 10 344 298 Б (~9,9 МиБ) | 2 755 556 Б (~2,6 МиБ) |
| `wasm_exec.js` (рантайм-загрузчик) | 16 992 Б | 4 365 Б |
| Релизный бинарник `torrentino` (весь бот) | 8 093 988 Б (~7,7 МиБ) | 3 394 291 Б (~3,2 МиБ) |

Вывод по размеру: даже «пустой» wasm-клиент по несжатому размеру больше всего серверного
бинарника, а по gzip — сопоставим. Это не фатально (2,6 МиБ скачиваются за доли секунды
в LAN), но это постоянная цена за каждую загрузку страницы (с учётом кэша — за первую),
и она на порядки больше, чем у htmx (десятки килобайт).

Важно: цифры зависят от версии Go и набора пакетов; с фреймворком (`go-app` и т.п.)
бинарник будет ещё больше. Замер минимального клиента — нижняя граница.

## 3. Как выглядел бы вариант

### 3.1. Артефакты и сборка

```
cmd/webui/main.go        // package main, GOOS=js GOARCH=wasm
web/static/app.wasm      // результат сборки
web/static/wasm_exec.js  // копия из $(go env GOROOT)/lib/wasm/
web/static/index.html    // оболочка: loading, <script>, загрузка wasm
```

```bash
GOOS=js GOARCH=wasm go build -trimpath -ldflags "-s -w" -o web/static/app.wasm ./cmd/webui
cp "$(go env GOROOT)/lib/wasm/wasm_exec.js" web/static/wasm_exec.js
```

`wasm_exec.js` **обязан** совпадать по версии с toolchain, иначе получаются трудно
диагностируемые ошибки инициализации рантайма. Это ещё одна пара «артефактов», которую
нужно синхронизировать при обновлении Go.

Оболочка: `WebAssembly.instantiateStreaming(fetch('{base}/static/app.wasm'))`, затем
`go.run(instance)`; до этого — экран загрузки/ошибки. `Content-Type: application/wasm`
обязателен. В деплое все пути — под `{base}/static/` (как и остальные ассеты).
Ассеты можно встроить в серверный бинарник через `embed` (тогда +~10 МБ к бинарнику)
или отдавать с диска (тогда меняется деплой: `update-service.sh` копирует ещё и
`app.wasm`/`wasm_exec.js`).

### 3.2. Клиентская архитектура

- Роутинг — `hash`/History API вручную или через `go-app`.
- Рендеринг — `syscall/js`: создание узлов, `textContent`, обработчики, `fetch`.
  Готового переиспользуемого рендерера от Telegram нет: `paginator` строит сообщения и
  inline-клавиатуры, а не DOM.
- Состояние — в памяти клиента; список, сортировка, фильтры, страница и выбор могут
  жить в браузере, а сервер отдаёт данные и выполняет действия.
- Данные — JSON API поверх тех же `core`-сервисов:

  ```
  GET  {base}/api/session
  GET  {base}/api/screens/{kind}
  POST {base}/api/screens/{kind}/commands   {cmd: "select:3"}
  GET  {base}/api/find?q=...
  GET  {base}/api/find/torrent?item=3
  POST {base}/api/actions                   {screen, item, action}
  ```

- Аутентификация/сессии/CSRF — те же, cookie `HttpOnly`, `X-CSRF-Token` в заголовке.
- PWA/офлайн возможны (service worker кэширует оболочку и wasm), но без сервера
  функционала нет: офлайн-режим даёт только «красивую заглушку».

### 3.3. Переиспользование кода

| Компонент | Переиспользуется? |
|---|---|
| `common/list` (List, View, сортировки/фильтры) | да, если останется UI-агностичным |
| `core` — модели и предикаты действий | да, но нужно отделить чистую модель от сервисов с `net/http` |
| `core` — сервисы (Jackett/Transmission/Torrserver) | нет: браузер не должен ходить в них напрямую (секреты, CORS) |
| `common/paginator` | нет: Telegram-специфичен |
| `html/template` | нет: DOM строится вручную |
| auth/session/CSRF | нет: серверная часть |

Отдельный важный вывод: для wasm всё равно нужен **чистый** пакет моделей/правил без
`net/http` и без Telegram. Это полезно и для SSR-варианта (Phase 0, `core`), но для wasm
требование жёстче: если `core` тянет `api/*` с `net/http`, клиент утащит в wasm лишний
код и получит соблазн ходить в сервисы напрямую.

## 4. Плюсы и минусы

### Плюсы

- Один язык и одна система типов для сервера и клиента.
- Можно переиспользовать `list.View`, модели элементов и правила доступности действий —
  меньше риска расхождения с Telegram.
- Нет npm/Node/сборщика фронтенда, нет фреймворк-чехарды; статическая типизация.
- WASM-клиент можно использовать как базу для PWA и офлайн-оболочки.
- JSON API остаётся полезным для других клиентов (CLI, мобильное приложение).

### Минусы

- Размер и холодный старт: ~2,6 МиБ gzip минимум + компиляция/инстанцирование
  (на слабых устройствах — заметно); SSR отдаёт готовый HTML сразу.
- DOM через `syscall/js` многословен; объём клиентского кода для паритета — тысячи строк.
  Фреймворки (go-app/Vecty/Vugu) сокращают boilerplate, но добавляют зависимость,
  свой роутинг/жизненный цикл и риск заброшенности.
- Дублирование рендеринга: Telegram-рендер и DOM-рендер всё равно разные; общим остаётся
  только состояние/правила.
- Отладка и профилирование хуже, чем у обычного Go/JS: нет source maps, стектрейсы
  в браузере, `-race` для wasm не работает; DOM-тесты требуют браузера.
- Нет SSR/прогрессивного улучшения: без JS пользователь видит только заглушку;
  доступность и клавиатурная навигация делаются вручную.
- CSP требует `'wasm-unsafe-eval'` для `script-src` — ослабление политики.
- Два артефакта и синхронизация `wasm_exec.js` с версией Go при обновлениях.
- Больше работы: +8–12 дней к SSR-варианту и постоянные затраты на поддержку.
- Ошибки в wasm-рантайме (panic) видны как сообщения в консоли, а не как аккуратный
  серверный 500 с request-id.

## 5. Сравнение вариантов

| Критерий | SSR + htmx (рекомендуется) | SPA на TypeScript | SPA на Go/WASM |
|---|---|---|---|
| Сборка | `go build` | Node + bundler | `go build` + копия `wasm_exec.js` |
| Размер первой загрузки | десятки КБ | сотни КБ | ~2,6 МиБ gzip |
| Холодный старт | нет | небольшой | сотни мс – секунды |
| Переиспользование Go-логики | полное (общая `core`/`list`) | нет (дублирование правил) | частичное (модели/`list`) |
| Рендеринг | шаблоны + автоэкранирование | свой | свой, через `syscall/js` |
| Тестируемость | высокая (httptest + HTML) | средняя (e2e) | средняя/низкая (нужен браузер) |
| Безопасность | CSP без eval, минимум JS | CSP сложнее | нужен `wasm-unsafe-eval` |
| Оценка | 22–31 день | +10–15 дней | +8–12 дней |
| Поддержка | низкая | средняя | средняя/высокая |

## 6. Решение

**Для v1 выбран SSR + htmx, WebAssembly не используется. Решение согласовано с
владельцем проекта.** Причины в порядке важности:

1. Задача — паритет с Telegram через браузер (в деплое — nginx/443, поддомен
   `torrentino.example.com`), а не офлайн-приложение. SSR даёт его дешевле и
   с меньшей поверхностью отказа.
2. Большая часть UI — списки и кнопки; сервер уже владеет данными и состоянием.
   Рендеринг на клиенте не даёт функционального выигрыша.
3. Размер/холодный старт и ослабление CSP — реальная цена без понятной выгоды.
4. Меньше кода и артефактов → проще тестировать, деплоить и поддерживать.
5. API-граница и UI-агностичный `list.View` оставляют возможность добавить SPA позже
   без переписывания доменной логики.

Пересмотреть решение стоит, если появится хотя бы одно из:

- требование работать офлайн/PWA (хотя полноценно без сервера всё равно нельзя);
- потребность в богатом клиенте: drag&drop, live-обновления без перезагрузки,
  сложные локальные состояния, мобильное приложение на том же API;
- несколько разнородных клиентов (CLI, мобильный, сторонний), для которых JSON API
  становится первичным;
- htmx/HTML-подход начнёт мешать (например, понадобится оптимистичный UI).

## 7. План миграции, если WASM будет выбран

1. Выделить `core/model` (элементы, действия, сортировки, фильтры) без `net/http`
   и без Telegram; сервисы оставить в `core/service`.
2. Добавить JSON API (см. 04, §11) поверх существующих сервисов; сессии/CSRF — те же.
3. Собрать `cmd/webui` на `syscall/js` (или go-app) с роутингом и компонентами;
   переиспользовать `common/list.View`.
4. Научить сборку/деплой собирать wasm и копировать `wasm_exec.js`; зафиксировать
   соответствие версии Go и загрузчика.
5. Оставить SSR-страницы как fallback (`{base}/classic` или при отсутствии JS) на
   переходный период; затем решить, убирать ли их.
6. Добавить e2e-тесты в браузере (Playwright/Chromedp) и проверку размера бандла в CI.

Оценка дополнительно к SSR-варианту: **+8–12 человеко-дней** (API 2–3, клиент 5–8,
сборка/тесты/деплой 1–2) и далее поддержка двух артефактов.

## 8. Альтернатива: TinyGo

TinyGo даёт wasm на порядок меньше (сотни килобайт), но это отдельный toolchain,
заметно урезанный stdlib (`net/http` и часть рефлексии поддерживаются ограниченно)
и иные ограничения рантайма.
Для проекта, который собирается обычным Go и не хочет второго компилятора, это плохой
компромисс. Рассматривать только если размер станет критическим требованием.

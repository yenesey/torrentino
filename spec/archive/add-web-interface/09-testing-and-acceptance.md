# 09. Тестирование и приёмка

## 1. Стратегия

Три уровня, без «тестов на всё»:

1. **Юнит-тесты** — чистая логика: `list.View`, парсер web-команд, пароли/сессии/CSRF,
   предикаты `core`, экранирование, санитайзинг имён и `next`.
2. **Интеграционные** — `httptest.Server` с фейковыми Jackett/Transmission/Torrserver,
   реальные middleware, сессии, шаблоны, фрагменты, коды ответов.
3. **Ручные/E2E** — браузерный сценарий паритета и «учения» при недоступном Telegram.
   Автоматический браузерный E2E (Playwright/Chromedp) — опционально: добавляет тяжёлую
   зависимость, но полезен для JS-части (опрос, фокус, удаление без подтверждения).

## 2. Юнит-тесты

| Область | Что проверять |
|---|---|
| `common/list` | `Select` (границы, отрицательные), `Next/Prev` на границах, `LastPage`, `ToggleSorting` (цикл 1→2→0, очередь), `ToggleFilter` (сброс страницы/выбора, «все выключены = всё видно»), `ExecuteSelected` без выбора/с невалидным индексом |
| `paginator.dispatch` | существующие тесты на пустые/битые callback-данные сохраняются; после рефакторинга они проверяют, что парсер вызывает те же методы `View` |
| `web/commands.go` | `select:`, `page:`, `sort:`, `filter:`, `controls:`, `action:`, `deselect`; мусор/переполнение/пустые payload → ошибка, без паники (fuzz) |
| `core/search` | `Compare`/`Stringify`, `AvailableActions` при разных комбинациях флагов, `ResolveHash` (есть/нет/ошибка), `Do` для download/series/movie/torrsrv |
| `core/downloads` | `Compare` (date/name/size/dir), `Stringify(Status)`, `AvailableActions` по статусам (downloading/seeding/paused/idle/unknown), `Delete` только для известного ID или безопасного пути |
| `core/torrsrv` | сортировка по размеру, `AvailableActions` |
| `web/auth` | PBKDF2 verify (ok/неверный/битый формат/неизвестный user), constant-time, dummy hash |
| `web/sessions` | создание/поиск/истечение idle и absolute, logout, лимит 512, хеш токена, ротация при логине |
| `web/csrf` | совпадение/несовпадение/пустой токен, Origin allow/deny, отсутствие Origin + валидный токен |
| `web` валидация | `next` (локальный/абсолютный/`//`/`javascript:`), `q` (длина/управляющие), имя `.torrent` (CR/LF/кавычки/длина) |
| `web` рендер | `<script>` в названии экранирован; `Details` с `javascript:` не становится ссылкой; emoji/aria |

| `web/basepath` | нормализация (`/`, `/torrentino`), отказ для `//`, `..`, хвостового `/`; `url()` helper |

## 3. Интеграционные тесты

Фейки:

- **Jackett** — `httptest` с JSON `{"Results":[...],"Indexers":[]}`; для web-тестов удобнее
  фейк-реализация интерфейса `core.JackettAPI` (без сети).
- **Transmission** — фейк `core.TransmissionAPI`; это главный аргумент за интерфейсы в
  Phase 0, потому что реальный клиент создаётся через `sync.Once` и «запоминает» хост.
- **Torrserver** — фейк `core.TorrserverAPI`.
- **Диск** — `t.TempDir()` с файлами/каталогами; `path.default/movie/series` указывают
  в него; `Statfs` работает на Unix (как и весь проект).

Сценарии:

1. Неавторизованный `GET {base}/find` → `303 {base}/login?next={base}/find`.
2. Логин: неверный пароль → 200 с общей ошибкой, сессии нет; верный → cookie + `303`.
   Проверить `Path={base}` и `Secure` при TLS-режиме.
3. Поиск: `POST {base}/find/search` → фрагмент, в нём результаты и «results: 1-N of M».
4. Выбор/сортировка/фильтр/страница через `{base}/ui/find/command` → меняется состояние,
   фрагмент корректен; устаревший индекс → 409.
5. Действия: download ставит `📥`, torrsrv ставит `🎦`, ошибка upstream → баннер + 502/200.
6. `/downloads`: список из Transmission + файлы на диске; футер; выключенный
   `Statfs` (несуществующий путь) не ломает страницу.
7. `/downloads` poll: фрагмент содержит прежние сортировку/фильтр/страницу.
8. Удаление сразу: один POST `action:delete` удаляет элемент; без CSRF — 403; повторный
   delete уже удалённого — 409, паники нет.
9. Автообновление и выбор: после poll строки переставились → выбор остался на том же
   элементе (по ключу), delete удаляет именно его; если элемент исчез — выбор снят/409.
10. Base path: основной режим `base=/` — `/find`, `/static/...` работают в корне
    поддомена; `next=/downloads` принимается. Fallback: при `base=/torrentino`
    `/torrentino/` открывается, `/torrentino` → 301/303 на `/torrentino/`, `/find` →
    404, `next=/torrentino/downloads` принимается, `next=/downloads` игнорируется.
11. `.torrent`: валидный bencode отдаётся с attachment; HTML/огромный ответ → 502/413;
    устаревший индекс → 409/404.
12. Истёкшая сессия на htmx-запросе → 200 + `HX-Redirect: {base}/login`.
13. Health/статика доступны без авторизации; `{base}/static/*` с версией кэшируется.
14. Несколько аккаунтов: два пользователя логинятся одновременно, сессии и экраны
    независимы; logout одного не трогает другого.
15. Параллельные запросы к одному экрану (`go test -race`): нет гонок, состояние
    консистентно, `-race` чистый.

Интеграционные тесты рендеринга используют `golang.org/x/net/html`/`htmlquery` (уже в
зависимостях) для проверки структуры, а не сравнения «простыней» HTML.

## 4. Паритет: golden-тесты

Идея: одна и та же последовательность команд, применённая к `list.View` с одинаковыми
элементами, должна давать одинаковые `Page`, `Selected`, порядок элементов и набор
фильтров — независимо от того, пришла команда из Telegram или из web.

```go
seqs := [][]string{
    {"select:2", "sort:Size", "page:next"},
    {"filter:TrackerId/rutor", "page:next", "page:prev"},
    {"sort:Size", "sort:Size", "sort:Size"}, // desc → asc → off
    {"select:3", "action:download", "select:3"}, // индекс после unselect
}
```

Каждая последовательность прогоняется через `list.View` напрямую (эталон) и через
оба парсера (Telegram dispatch / web commands). Результаты сравниваются по:

- `Len()`, `Bounds()`, `Page`, `Selected`;
- списку ID элементов в порядке отображения;
- значениям фильтров и очереди сортировки.

Это ловит расхождения, которые не видны в UI-тестах, и защищает от повторения истории
с `lastPage` и паниками на callback-данных.

## 5. Безопасность

| Тест | Ожидание |
|---|---|
| POST без CSRF | 403, состояние не изменилось |
| POST с чужим Origin | 403 |
| Cookie без `HttpOnly`/`SameSite` | не должно быть (проверка заголовка `Set-Cookie`) |
| Cookie `Path` | `/` для поддомена (host-only, без `Domain`), `/torrentino` в fallback |
| XSS-название `<img src=x onerror=...>` | в HTML — текст, тега нет |
| `Details: javascript:alert(1)` | ссылка не рендерится |
| `next=//evil`, `next=https://evil` | игнорируется → `{base}/find` |
| `next=/downloads` (base=`/`) | принимается |
| `next=/torrentino/downloads` (base=`/`) | игнорируется как путь вне base |
| `next=/torrentino/downloads` (base=/torrentino) | принимается |
| Path traversal в delete | 409/ошибка, файл вне корня не удалён |
| Rate limit логина | после N неудач — 429 с `Retry-After` |
| Сессия после logout | 303 на логин, старый токен не работает |
| Фиксация сессии | после логина токен другой |
| `/healthz` | не раскрывает версии/конфиг |
| CSP | нет `unsafe-inline`/`unsafe-eval` (для SSR-варианта) |
| Логи | нет паролей/токенов/cookie (grep по тестовому логу) |

## 6. Нагрузка и устойчивость

- 10 вкладок `/downloads` с опросом 5 с: Transmission/диск опрашиваются не чаще ~1 раза
  в 2 с (кэш снимка); сервер не растёт по памяти.
- Поиск с задержкой фейка 2–5 с: UI показывает прогресс, отмена запроса клиентом
  освобождает горутину (проверить с `r.Context()`).
- 100 последовательных команд: без утечек горутин, `-race` чистый.
- Лимит сессий: 513-я вытесняет старейшую, без паники.
- Долгий upstream (60 с) не блокирует другие экраны/сессии.

## 8. Учения «Telegram недоступен»

Цель — доказать, что веб не зависит от Telegram.

1. Собрать бинарник `go build -o /tmp/torrentino-drill .`.
2. Создать каталог `/tmp/web-drill`, положить туда копию `settings.json` с:
   - `telegram-api-token: "0:invalid"` (Telegram заведомо не отвечает);
   - `web.enabled: true`, `listen: "127.0.0.1:18088"`, `base-path: "/"`,
     `secure-cookies: false` (локальный HTTP), два тестовых пользователя;
   - `path.*` — временные каталоги.
3. Запустить из этого каталога: `./torrentino-drill`.
4. Убедиться: в логе — ошибки Telegram, процесс жив;
   `curl 127.0.0.1:18088/healthz` → 200.
5. Войти в браузере, выполнить полный сценарий: поиск → download (в temp) → пауза →
   старт → удаление (сразу, без подтверждения) → torrsrv add/delete → `.torrent`.
   Проверить, что после удаления элемент исчезает, а повторный delete даёт 409.
   Использовать отдельный профиль браузера: cookie не учитывает порт, и сессия учения
   может перетереть сессию боевого экземпляра на том же хосте.
6. Войти вторым пользователем в другом профиле: его список/страница/сортировка
   не зависят от первого; logout одного не разлогинивает второго.
7. Убедиться, что в HTML/логах нет секретов, а действия не зависят от Telegram API.
8. Перезапустить процесс: сессии пропали (ожидаемо), повторный вход работает.

Дополнительно (опционально): заблокировать egress к Telegram на уровне firewall и
повторить п. 4–5, чтобы исключить случайный успех `getMe`.

## 9. Критерии приёмки

1. Сценарий из §8 проходит полностью.
2. Все строки матрицы 02 закрыты; каждое отступление описано и принято.
3. `go vet ./...`, `go test -race ./...`, `go build ./...` — чисто.
4. Новые пакеты (`core`, `common/list`, `web`) покрыты юнит/интеграционными тестами
   по §2–3.
5. Вход/выход/истечение сессии работают; все защищённые маршруты возвращают 401/303.
6. CSRF: мутация без токена/с чужим Origin отклоняется.
7. Удаление выполняется сразу, как в Telegram; требует валидной сессии и CSRF;
   удаление вне разрешённых путей отклоняется; выбор не «съезжает» после poll.
8. XSS-название и `javascript:`-ссылка безопасны; CSP без `unsafe-*` (SSR).
9. `/downloads` обновляется каждые ~5 с, состояние списка не сбрасывается; скрытая
   вкладка не опрашивает сервер.
10. Ошибки Jackett/Transmission/Torrserver показываются в UI и не ломают страницу.
11. Telegram-сценарий не изменился (smoke из §7).
12. `settings.json` без блока `web` работает как до изменений; при `enabled: true` и
    некорректных полях — fail-fast с понятным списком.
13. Логи не содержат паролей/токенов/cookie; аудит удалений есть.
14. Graceful shutdown: SIGTERM не рвёт активные запросы мгновенно, сервер закрывается
    за ≤ 10 с.
15. Все URL, формы, редиректы, cookie и статика работают на
    `https://torrentino.example.com/` (base `/`); старый
    `/torrentino` на базовом домене отдаёт 301 на поддомен; nginx-конфиг из 08
    проходит проверку.
16. Несколько веб-аккаунтов работают одновременно и независимо.
17. Документация обновлена: `readme.md`, `AGENTS.md` (новые пакеты, конфиг, правила
    импортов), пример конфига.

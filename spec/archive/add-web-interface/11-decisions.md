# 11. Журнал решений (ADR)

Формат: контекст → решение → следствия. Альтернативы указаны для тех решений, где они
реально рассматривались.

---

## D1. Веб-сервер в том же процессе и бинарнике

**Контекст.** Нужен второй UI, использующий те же `Settings` и клиентов Jackett/
Transmission/Torrserver. Отдельный процесс потребовал бы второго бинарника, второго
конфига или IPC.

**Решение.** HTTP-сервер запускается из `main()` в том же процессе; включается
`web.enabled`. При включённом web ошибка инициализации Telegram-бота не фатальна.

**Следствия.**
- Один systemd-юнит, прежний `update-service.sh`, общий конфиг.
- Веб и бот делят судьбу процесса; при панике/рестарте оба недоступны на секунды.
- При выключенном web поведение полностью прежнее.

**Альтернатива.** Отдельный `torrentino-web` с собственным конфигом — отклонено:
дублирование конфигурации и клиентов, более сложная эксплуатация без выигрыша для
домашнего NAS.

---

## D2. Server-side rendering на `html/template` + htmx

**Контекст.** UI — списки, кнопки, сортировки и фильтры; состояние уже живёт на сервере.
Нужен минимум кода и зависимостей, безопасное экранирование и работа без сборки фронтенда.

**Решение.** Go-шаблоны + вендорный htmx 2.x + небольшой `app.js` (опрос, CSRF, фокус).
Формы работают и без JS (обычный POST + 303).

**Следствия.**
- Нет npm/Node, нет отдельного бинарника, автоэкранирование из коробки.
- Частичные обновления через HTML-фрагменты; сервер — источник истины.
- htmx фиксированной версии, `allowEval=false`, CSP без `unsafe-eval`.

**Альтернативы.** SPA на TypeScript (тяжелее, дублирование правил) и Go/WASM (D3) —
отклонены для v1.

---

## D3. WebAssembly не используется в v1

**Контекст.** Запрос «рассмотреть вариант на WebAssembly». Спайк: минимальный Go/wasm
клиент — 10,3 МБ (2,7 МБ gzip), больше релизного бинарника бота; DOM-рендеринг и тесты
сложнее; CSP требует `wasm-unsafe-eval`.

**Решение.** SSR+htmx; wasm не включается. API-граница и UI-агностичный `list.View`
оставляют возможность добавить SPA позже. Решение согласовано с владельцем проекта.

**Следствия.** Меньше артефактов и поддержки; нет офлайн/PWA; пересмотр — при появлении
триггеров из 07, §6.

---

## D4. Состояние экранов на сервере, по одному на сессию и тип

**Контекст.** Telegram-пагинатор хранит состояние в замыкании и глобален на процесс —
одновременные пользователи мешают друг другу. Для web нужна изоляция.

**Решение.** `Session` хранит по одному `Screen` на `Kind`; `Screen` содержит
`list.View` (элементы, сортировка, фильтры, страница, выбор) и `SelectedKey` —
стабильный ключ выбранного элемента. Сессии in-memory.

**Следствия.**
- Пользователи и сессии не пересекаются; рестарт = потеря сессий.
- Выбор переживает автообновление: действие адресуется элементу, а не индексу,
  поэтому удаление не может «съехать» на соседнюю строку.
- Несколько вкладок одного типа делят состояние (ограничение v1).
- Нет персистентности и внешнего хранилища.

**Альтернатива.** Клиентское состояние в URL/JSON — отклонено: поиск дорогой, состояние
сложное, пришлось бы кэшировать результаты и менять семантику действий.

## D5. Собственные веб-аккаунты, независимые от Telegram

**Контекст.** `users-list` — Telegram ID; при недоступном Telegram вход через него
невозможен. Вход должен работать без Telegram API.

**Решение.** `web.users` с несколькими равноправными аккаунтами и PBKDF2-хешами
(stdlib `crypto/pbkdf2`), серверные сессии, CSRF, rate limit. `users-list` не
переиспользуется.

**Следствия.**
- Вход не зависит от Telegram; пароли хранятся только хешами.
- Несколько человек работают одновременно, у каждого своя сессия.
- Нет регистрации/сброса/2FA; смена пароля — правка конфига + рестарт.
- Нужен генератор хеша (`-hash-password`).

**Альтернатива.** Общий пароль на всех — отклонено: нет имён для аудита и слабее
управление; Telegram-вход — не работает при недоступном Telegram.

---

## D6. Опрос `/downloads` раз в 5 с вместо SSE/WebSocket

**Контекст.** В Telegram экран загрузок обновляется тикером 5 с. Опрос — простейший
способ повторить это в браузере.

**Решение.** htmx/JS опрос фрагмента каждые 5 с; пауза при скрытой вкладке; серверный
кэш снимка 2 с.

**Следствия.**
- Нет состояния соединения, реконнектов, отдельных горутин на клиента.
- Задержка до 5 с, как и раньше; при ошибке — старый список и предупреждение.
- SSE можно добавить позже без изменения контракта страницы.

---

## D7. Общий UI-агностичный `list.View` и `core`

**Контекст.** Сортировки/фильтры/пагинация и правила доступности действий нетривиальны;
дублирование между Telegram и web гарантирует расхождения.

**Решение.** Phase 0: перенос `List`/`Sorting`/`Evaluator` в `common/list`, добавление
`View` с операциями `Select/NextPage/ToggleSorting/ToggleFilter/ExecuteSelected`;
доменные элементы/действия/сервисы — в `core`. Оба UI рендерят одно состояние.

**Следствия.**
- Одна реализация семантики, общие golden-тесты, меньше риска регрессии.
- Требуется аккуратный рефакторинг `paginator` и хендлеров до начала web.
- `paginator` остаётся Telegram-рендерером.

---

## D8. Встроенные ассеты и шаблоны (`embed`)

**Контекст.** Деплой — один бинарник, копируемый в `/opt/torrentino`; внешние файлы
усложняют обновление и создают рассинхронизацию версий.

**Решение.** `go:embed` для `templates/` и `static/` (включая htmx); версия в query.

**Следствия.**
- Один артефакт, атомарное обновление, откат бинарником.
- Изменение статики требует пересборки (приемлемо).
- Бинарник немного растёт (десятки КБ; wasm сюда не входит — D3).

## D9. Основной деплой — поддомен `torrentino.example.com`

**Контекст.** Доступ нужен из интернета по домену; на 443 уже работают два других
приложения через nginx. Общий origin с ними означал бы, что их скрипты могут читать
наши страницы и CSRF-токены (T15). Прямая публикация порта приложения нежелательна.

**Решение.** `torrentino` слушает `127.0.0.1:8088`, TLS терминирует nginx, приложение
не публикуется напрямую. Основной origin — `https://torrentino.example.com/`
с `base-path: "/"` и отдельным сертификатом. `secure-cookies: true`,
`trusted-proxies` содержит адрес прокси, HSTS — на nginx. Старый путь
`/torrentino` на базовом домене — только `301` на поддомен. Встроенный TLS
(`tls.cert/key`) остаётся для варианта без прокси.

**Следствия.**
- Поддомен — отдельный origin: T15 закрыт, cookie host-only.
- Пароль и cookie идут только по HTTPS; порт 8088 недоступен из интернета.
- Нужен отдельный сертификат и его автопродление (текущий сертификат базового домена
  поддомен не покрывает).
- Нужна конфигурация nginx (`server`, заголовки, таймауты) — 08, §5.2–5.3.

**Альтернатива.** Путь `/torrentino` на базовом домене — отклонён как основной:
оставляет общий origin и риск T15. Поддержка `base-path` сохранена только как fallback
(§5.4).

## D10. Удаление сразу, как в Telegram (без подтверждения)

**Контекст.** Удаление через Transmission уничтожает локальные данные, а для файлов
только на диске — безвозвратно. При этом владелец выбрал паритет с Telegram, где
удаление выполняется одним нажатием.

**Решение.** `action:delete` выполняется сразу: POST + CSRF + проверка `Origin`.
Действие адресуется выбранному элементу по стабильному ключу (`id:`, `path:`, `hash:`),
сервер проверяет, что элемент ещё в списке, и что путь лежит внутри `path.*`; пишется
аудит. Отдельного экрана подтверждения и `confirm=1` нет.

**Следствия.**
- Паритет с Telegram; меньше кликов и кода.
- Случайный клик может удалить данные — риск принят и зафиксирован в 06, §15;
  компенсируется красной кнопкой с `title`, аудитом и будущими read-only/корзиной.
- Выбор по ключу защищает от удаления соседней строки после автообновления.
- CSRF/Origin защищают от чужой страницы, но не от самого пользователя.

**Альтернатива.** Двухшаговое подтверждение (было в черновике) — отклонено владельцем
как расходящееся с Telegram.

## D11. JSON API отложен до появления клиента

**Контекст.** SSR-страницы покрывают v1; JSON API нужен только SPA/WASM или внешним
клиентам.

**Решение.** В v1 только HTML-эндпоинты. Если появится SPA — добавить
`{base}/api/*` поверх тех же `core`/`list.View`, сохранив HTML как fallback.

**Следствия.** Меньше поверхности и тестов сейчас; миграция не требует переписывания
доменной логики.

---

## D12. `web.base-path`: основной `/`, fallback `/torrentino`

**Контекст.** Основной деплой — поддомен, где префикс не нужен. Но поддержка префикса
полезна как fallback (если поддомен/сертификат временно недоступны), для локальной
разработки и для тестов; кроме того, старый путь `/torrentino` нужно уметь
редиректить.

**Решение.** `web.base-path` (по умолчанию `/`) остаётся настраиваемым. В основном
деплое — `/`: `url()` возвращает путь как есть, `StripPrefix` не используется, cookie
host-only `Path=/`. В fallback — `/torrentino`: приложение принимает только пути под
префиксом, снимает его `StripPrefix`, cookie получает `Path=/torrentino`, `next`
ограничен префиксом. nginx в fallback передаёт путь без обрезки (`proxy_pass` без
завершающего `/`); при основном деплое старый путь на базовом домене — `301` на
поддомен.

**Следствия.**
- Основной режим проще: нет префикса в URL и cookie.
- Все шаблоны/редиректы обязаны использовать `url()` helper; хардкод `/find` — баг.
- Нужны тесты обоих режимов (`/` и `/torrentino`) и проверка nginx.
- Fallback с путём возвращает same-origin риск (06, T15), поэтому он не равноценен
  поддомену.
